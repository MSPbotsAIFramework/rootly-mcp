## Requirement understanding

One line: Command incidents, write post-mortems, manage on-call, and track action items via Rootly.

The ticket (list: Agent Platform Client feedback) asks that the AI agent be able to use Rootly,
an incident-management and on-call platform, to drive incidents end to end, write and update
post-mortems (retrospectives), see and manage on-call coverage, and create/track action items
(follow-up tasks) coming out of incidents. The linked `conduit.wyre.ai/plugins/rootly` page is
generic marketing copy for Rootly and adds no requirement detail beyond the one line above (see
Sources in Current state).

## Current state

- `MSPbotsAIFramework/rootly-mcp` already exists and is MSPbots' Rootly MCP connector
  (`main` @ `5e9e0b7`, 2026-10-23). It implements: incidents (list/get/create/update/resolve),
  alerts (list/create/acknowledge/resolve/update), on-call schedules (list/get of the schedule
  record only — not who is on call right now), and teams/severities/current-user
  (`README.md:104-139` tool table; `src/rootly_mcp/tools/{incidents,alerts,schedules,org}.py`).
- `grep -rniE "postmortem|post-mortem|post_mortem|action_item|retrospective" src/ tests/`
  (run 2026-10-30 against `main@5e9e0b7`) returns no hits — confirmed against the code, not just
  the README, that post-mortems and action items are not implemented.
- "Manage on-call" is partly covered: `rootly_schedules_list`/`rootly_schedules_get`
  (`src/rootly_mcp/tools/schedules.py:25-44`) read a schedule's own configuration, but there is no
  tool to see who is on call right now, and no tool to reassign on-call coverage (an override) —
  both are the two actions an incident responder actually performs on-call, day to day.
- wiki: `ProductDocs` has no Rootly-specific page (`mbp.py wiki find Rootly` → no hits, 2026-10-30;
  `wiki find connector` lists only platform/connector-UI pages, not vendor-specific facts) —
  Rootly is not covered by the wiki.
- Rootly's public REST API (v1, JSON:API) confirms both the gap and the fix: endpoints exist for
  `GET/PUT /v1/post_mortems(/{id})` (retrospectives) and
  `GET/POST/PUT/DELETE /v1/action_items`, `/v1/incidents/{incident_id}/action_items`. Source:
  Rootly's published OpenAPI document at
  `https://rootly-heroku.s3.amazonaws.com/swagger/v1/swagger.json`, fetched 2026-10-30 — the same
  source the connector's own "Built on the published API reference" delivery note already points
  to (`README.md:198`).
- There is **no** `POST /v1/post_mortems` in Rootly's API: a retrospective is created automatically
  by Rootly when an incident starts, not via the API. "Write post-mortems" is therefore served by
  list + get + update, not a create tool (see Non-goals, Data & API contract).

## Product design

### Goals

- G1: An agent can read and update an incident's post-mortem (retrospective): title, status
  (draft/published) and content.
- G2: An agent can see every action item in the org or on one incident, create a new action item
  on an incident, and update one (status, assignee, due date, priority, description) to track it
  to completion.
- G3: An agent can see who is on call right now, and hand off on-call coverage for a time window
  (an on-call override) without going through the Rootly UI.

### Non-goals

- NG1: Retrospective templates (`post_mortem_templates`) — this ticket is about writing one
  incident's post-mortem, not managing the templates it is created from.
- NG2: Full schedule/rotation authoring (create/update/delete schedules, rotations, rotation
  members, active days) — out of scope. "Manage on-call" is read as "see who's on call" + "hand
  off coverage", not "build a new on-call rotation", which is a one-time admin task better done in
  the Rootly UI (see Open questions).
- NG3: On-call pay reports, on-call roles, on-call shadowing, shift-coverage requests — none of
  these are implied by "manage on-call" in the ticket, and each is its own separate admin
  workflow in Rootly.
- NG4: Deleting action items. "Track" implies a status lifecycle (open → in_progress →
  done/cancelled via update), not removal; no delete tool is added.
- NG5: Registering Rootly in the MCP gateway's credential registry — a one-time operational step
  handled when the connector is deployed (`mcppub register`, already flagged pending in
  `README.md:208-209`), not a product capability this ticket changes.

### Acceptance criteria

(Given/When/Then, verified by calling the MCP tools over `/mcp` — the only interface this server
has; there is no UI.)

- AC1: Given the server is running, When a client calls `tools/list`, Then the 9 new tools listed
  in Tech design §4 (Change list) appear with the parameters given in §5 (Data & API contract).
- AC2: Given an incident whose retrospective is still `draft` and has never been opened in
  Rootly's collaborative editor, When the agent calls `rootly_postmortems_update` with a new
  title/content, Then the call succeeds and a following `rootly_postmortems_get` shows the new
  values.
- AC3: Given a retrospective already opened in Rootly's collaborative editor (so Rootly owns the
  body), When `rootly_postmortems_update` is called with new content, Then the tool returns a
  structured, non-crashing error naming the conflict (Rootly's `409`), not an unhandled exception.
- AC4: Given a post-mortem id that does not exist, When `rootly_postmortems_get` or
  `rootly_postmortems_update` is called, Then the tool returns the existing `not_found` error
  envelope (no new error shape).
- AC5: Given an incident id, When `rootly_action_items_create` is called with a summary, Then
  Rootly creates the action item under that incident and the tool returns its id and status.
- AC6: Given action items exist across the org, When `rootly_action_items_list` is called with no
  `incident_id` and a status or priority filter, Then only matching items are returned, paginated
  the same way every other list tool in this server already paginates
  (`items/count/total/page/has_more`, with `offset`/`next_offset`).
- AC7: Given an open action item, When `rootly_action_items_update` is called with
  `status: "done"`, Then Rootly marks it done and the tool returns the updated record.
- AC8: Given no schedule filter, When `rootly_oncalls_list` is called, Then it returns who is on
  call right now, grouped by escalation policy, in the same flattened shape every other resource
  in this server returns.
- AC9: Given a schedule id, a user id and a start/end time, When
  `rootly_schedules_override_create` is called, Then Rootly reassigns on-call coverage for that
  window; calling it again with the same user and times returns the existing override rather than
  creating a duplicate (Rootly's own idempotency, per the API's documented behavior).
- AC10: Given a required field is missing or invalid for a write tool added by this ticket, When
  it is called, Then the existing `invalid_argument` error envelope is returned, not an unhandled
  exception.
- AC11: Given no `X-Rootly-Api-Token` header, When any new tool is called, Then the existing
  gateway middleware still returns `401` before the tool runs — no new code path to protect
  (`src/rootly_mcp/server.py:84-109`).

### Open questions

- [assumed, not blocking] "Manage on-call" is read narrowly as "see who's on call" +
  "hand off coverage via an override" (G3, AC8-9), not full rotation/schedule authoring (NG2). If
  the reporter actually wants rotation management, Tech design §3/§10 would need a second pass.
  This reading covers the two actions an incident responder actually needs during an incident,
  which is the stated use case ("Command incidents... manage on-call").
- [not blocking] Whether a post-mortem's `id` equals its incident's id, or must always be
  looked up via `rootly_postmortems_list`, is not stated in the Rootly API reference consulted at
  design time. It does not change the product behavior either way (the agent always has a working
  `rootly_postmortems_list` → id → get/update path) and is left for the dev leg to confirm against
  a live token (Tech design §11, Risks).
- [not blocking] No delete tool for action items (NG4). If later feedback asks for it,
  `DELETE /v1/action_items/{id}` already exists in Rootly's API and can be added as a small
  follow-up.

## Tech design

### 1. Conclusion

Add three tool modules to the existing per-domain architecture: `postmortems.py` and
`action_items.py` are new, `schedules.py` gains two more tools. This follows exactly the pattern
the repo already uses in `incidents.py` / `schedules.py` / `org.py`: a `register(mcp,
client_factory)` function per module, `run_tool` for the error-envelope wrapper, and
`single`/`list_page`/`body`/`resource_id`/`compact`/`enum_value` from `_common.py` for JSON:API
shaping, over the existing `RootlyClient.get/request`. No new abstractions, no new error-handling
layer, no new HTTP client — this is additive work inside an architecture that already does
everything these tools need.

### 3. Option analysis

No real alternative to the module-per-domain shape: `server.py:131` iterates a fixed module list;
adding a module is the architecture's designed extension point. The one choice worth recording is
*where* the two on-call tools go:

| Option | Do | Pros | Cost | Verdict |
|---|---|---|---|---|
| A | Add `rootly_oncalls_list` + `rootly_schedules_override_create` to the existing `schedules.py` / `schedules` domain | One fewer domain for the agent to discover via `rootly_navigate`; both tools take a `schedule_id`, matching Rootly's own data model | `schedules.py` grows from 2 to 4 tools | **Chosen** |
| B | New `oncalls.py` module / domain, mirroring Rootly's own `OnCalls`/`OverrideShifts` API tags | Mirrors the vendor's own API grouping | A 4th domain for 2 tools is more navigation overhead than it saves | Rejected |

Post-mortems and action items each get their own module/domain rather than folding into
`incidents.py`, for the same reason `alerts.py` is its own module despite alerts being
incident-adjacent too: action items are also listed **org-wide**
(`GET /v1/action_items`, not incident-scoped) and post-mortems have their own lifecycle
(draft/published) independent of the incident's own status. Bundling either into `incidents.py`
(already 5 tools) would mix concerns the existing per-resource-module pattern deliberately keeps
apart.

### 4a. Reuse & cleanup

### 5. Data & API contract

All calls use `Authorization: Bearer <token>` (unchanged) against `https://api.rootly.com/v1`
(`config.py:18`), JSON:API media type (`config.py:19`). Source: Rootly's published OpenAPI
document (`https://rootly-heroku.s3.amazonaws.com/swagger/v1/swagger.json`, fetched 2026-10-30;
the README's existing "Built on the published API reference" note, `README.md:198`, already names
this as the project's source of truth).

**Post-mortems** (Rootly calls these "incident retrospectives" in its UI; the API still uses
`post_mortems` / resource type `incident_post_mortems`):

- `GET /v1/post_mortems?filter[status]=&filter[search]=&page[number]=&page[size]=` →
  `{"data": [{"id", "type": "incident_post_mortems", "attributes": {title, status, content,
  started_at, resolved_at, mitigated_at, created_at, updated_at, url, show_*}}], "meta":
  {"total_count", "total_pages"}, "links": {...}}`.
- `GET /v1/post_mortems/{id}` → same shape, single resource; `404` if not found.
- `PUT /v1/post_mortems/{id}` body `{"data": {"type": "incident_post_mortems", "attributes":
  {"title"?, "content"?, "status"? ("draft"|"published")}}}` → `200` with the updated resource;
  `404` not found; **`409`** if the body is already owned by Rootly's collaborative editor (AC3);
  `503` if the collaborative document state could not be verified. Both fall through to the
  existing generic `classify_status` mapping (`invalid_argument` / `upstream_error`
  respectively, `api_client.py:78-85`) — no new error code needed.
- Tool mapping: `rootly_postmortems_list` → `GET /v1/post_mortems`;
  `rootly_postmortems_get(postmortem_id)` → `GET /v1/post_mortems/{id}`;
  `rootly_postmortems_update(postmortem_id, title?, content?, status?)` → `PUT
  /v1/post_mortems/{id}`.
- No `POST /v1/post_mortems` exists (Current state) — there is no create tool for this resource.

**Action items**:

- `GET /v1/action_items?filter[status]=&filter[priority]=&filter[kind]=&page[number]=&
  page[size]=` (org-wide) → `{"data": [{"id", "type": "incident_action_items", "attributes":
  {summary, description, kind ("task"|"follow_up"), priority ("high"|"medium"|"low"), status
  ("open"|"in_progress"|"cancelled"|"done"), due_date, assigned_to, created_by, jira_issue_*,
  created_at, updated_at}}], "meta", "links"}`.
- `GET /v1/incidents/{incident_id}/action_items?page[number]=&page[size]=` (incident-scoped, no
  status/priority/kind filters) → same item shape, no `meta`/`links` (per the swagger path
  definition — confirmed it lists `include`/`page[number]`/`page[size]` only).
- `GET /v1/action_items/{id}` → single resource; `404` if not found.
- `POST /v1/incidents/{incident_id}/action_items` body `{"data": {"type":
  "incident_action_items", "attributes": {"summary" (required), "description"?, "priority"?,
  "due_date"?, "assigned_to_user_id"?}}}` → `201`; `401` missing/invalid token; `422` invalid.
- `PUT /v1/action_items/{id}` body `{"data": {"type": "incident_action_items", "attributes":
  {any of the above, plus "status"?}}}` → `200`; `404`; `422`.
- Tool mapping: `rootly_action_items_list(incident_id?, status?, priority?, kind?, limit?,
  page?, offset?)` → `GET /v1/action_items` or `GET /v1/incidents/{incident_id}/action_items`
  depending on `incident_id` (§4); `rootly_action_items_get(action_item_id)` → `GET
  /v1/action_items/{id}`; `rootly_action_items_create(incident_id, summary, description?,
  priority?, due_date?, assigned_to_user_id?)` → `POST /v1/incidents/{incident_id}/action_items`;
  `rootly_action_items_update(action_item_id, status?, priority?, description?, due_date?,
  assigned_to_user_id?)` → `PUT /v1/action_items/{id}`.

**On-call**:

- `GET /v1/oncalls?filter[schedule_ids]=&filter[user_ids]=&since=&until=&earliest=&time_zone=` →
  `{"data": [{"id", "type": "on_call_resources", "attributes": {schedule_id, schedule_name,
  user_id, escalation_policy_id, escalation_policy_name, escalation_level, notification_type,
  starts_at, ends_at}}]}` — **no `meta`/`links`**, unlike every other list in this server (§4).
- `POST /v1/schedules/{schedule_id}/override_shifts` body `{"data": {"type": "shifts",
  "attributes": {"starts_at", "ends_at", "user_id"}}}` (all three required) → `200` if an
  identical override already exists (returned, not duplicated), `201` created; `401`; `422`
  ("cannot create schedule-based override shift").
- Tool mapping: `rootly_oncalls_list(schedule_id?, user_id?, since?, until?)` → `GET /v1/oncalls`;
  `rootly_schedules_override_create(schedule_id, user_id, starts_at, ends_at)` → `POST
  /v1/schedules/{schedule_id}/override_shifts`.

**Backward compatibility**: purely additive — no existing tool's name, parameters or return shape
changes. No DB: this server is stateless (`server.py:125`, `stateless_http=True`), so there is no
persistence layer or migration to consider.

### 6. Key flow / sequence

Example: "find the incident, write its post-mortem, and open a follow-up action item."

1. Agent → `rootly_incidents_list(status="resolved")` (existing) → gets `incident_id`.
2. Agent → `rootly_postmortems_list(search="<incident title>")` (new) → gets `postmortem_id`
   (see Open questions on whether this lookup can ever be a direct id match instead).
3. Agent → `rootly_postmortems_update(postmortem_id, content="<html>", status="published")`
   (new) → Rootly saves the retrospective.
4. Agent → `rootly_action_items_create(incident_id, summary="Add a dashboard alert for X")`
   (new) → Rootly creates the follow-up, later visible via `rootly_action_items_list(incident_id)`.

Each step is one stateless HTTP round trip through the unchanged
`GatewayCredentialsMiddleware → RootlyClient.request → Rootly API` path (`server.py:84-115` →
`api_client.py:121-163`); nothing in this ticket introduces multi-step server-side state.

### 7. Non-functional

- **Idempotency & concurrency**: reads are naturally idempotent. `rootly_postmortems_update` and
  `rootly_action_items_update` are `WRITES_IDEMPOTENT` (repeat calls converge to the same state,
  matching `rootly_incidents_update`'s own annotation). `rootly_action_items_create` is `WRITES`,
  not idempotent — two calls make two action items, same as `rootly_incidents_create`.
  `rootly_schedules_override_create` is `WRITES_IDEMPOTENT` because Rootly itself de-duplicates
  identical overrides server-side (§5) — no client-side idempotency key is needed. No per-request
  state is kept anywhere in this server (`stateless_http=True`); nothing here changes that.
- **Performance**: no new hot paths — these are low-frequency, user-triggered calls, the same
  class as the existing 19 tools. `GET /v1/action_items` is org-wide and can be large; it is
  paginated like every other list tool (`list_page`, default page size 25, max 100), and
  `dump_json_capped` (`_json.py:30-151`) already protects every tool's response against flooding
  the agent's context regardless of upstream page size.
- **Security**: no new credential or header — same `X-Rootly-Api-Token` →
  `Authorization: Bearer` flow (`server.py:88-115`, `api_client.py:124`), same per-request-only
  storage (`contextvars`, reset in `finally`, `server.py:104-108`), same shared, credential-free
  HTTP connection pool (`api_client.py:37-62`). No secrets are logged — `api_client.py:144-147`
  logs method/path/status only.
- **Multi-tenant isolation**: unchanged — every request carries its own caller's token and nothing
  is cached or shared across requests/tenants (`api_client.py:37-39` states this explicitly for
  the existing tools; the same client class is reused unmodified by the new tools).
- **Observability**: `run_tool` already logs `tool=<name> outcome=... ms=...` for every call
  (`_common.py:171-179`) and `RootlyClient.request` logs every upstream call
  (`api_client.py:144-147`) — the new tools get this for free by using the same helpers; no new
  logging code is needed.

### 8. Rollout & rollback

Single repository, single deploy unit; MCP repos have no feature-flag mechanism
(`mcp-track.md`). Release order: no dependency — this ticket does not touch any other repository
(`release order: any`, though moot with one repo). Rollout follows the standard MCP-track path:
the review leg merges `dev/PRD-21240` into `main`, re-syncs and re-tests, then calls `mcppub
publish` to redeploy INT with the new `main` (`mcp-track.md` §4.4/§4.8). Rollback is `git revert`
the merge commit and republish — purely additive tools, so rolling back only removes 9 tools from
`tools/list`; there is no data migration and no in-flight state to worry about (stateless server).

### 11. Risks & dependencies

- **Risk**: the post-mortem/incident id relationship (Open questions) is unconfirmed against a
  live account; if a postmortem cannot be found from an incident at all without an undocumented
  endpoint, G1's usefulness narrows to "edit a retrospective you already have the id for" — not
  blocking (the list tool always works), but worth confirming early in implementation rather than
  at the end.
- **Risk**: `/v1/oncalls` is a comparatively heavier-query endpoint (many filter params,
  policy-level grouping); if an org has escalation-policy shapes this server has never modeled,
  the flattened output may need a second look. Mitigated by `dump_json_capped` already handling
  oversized/odd-shaped responses safely.
- **Dependency**: none on other tickets or repositories. Depends only on Rootly's public v1 API
  remaining as documented in the swagger source cited throughout this design (fetched 2026-10-30).
  The README's own "Corrections compared with the older version" delivery note
  (`README.md:198-203`) shows this API has drifted before, so the dev leg should re-verify the
  exact request/response shape against a live call, not just the swagger document, before
  considering G1-G3 done.
